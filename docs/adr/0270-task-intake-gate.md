# ADR-0270：任务受理门契约

## 状态

**Proposed — 2026-10-02（草稿）**

> **一句话**：Muse 的"接任务前 7 问"不是文档，是每 turn 注入的受理门——LCA 的 run 时路径上这道门是真空的：
> 7 问只存在于 dev 侧 AGENTS.md，agent 自己的 prompt 装配里没有任何等价约束。

## 0. 对齐来源：ADR-0255 §0

0255 §0 定义"接任务前 7 问"（问题是什么 / 受影响的事实或契约 / 唯一真值 /
改变哪个边界 / 现有机制能否表达 / 失败·重试·幂等 / 如何验证），其机制形态是
**每 turn 注入的 standing 义务**。"必答，不答不写"是字面语义：工具调用之前，
先在轨迹里给出 7 问答案。

实证（生产 Muse 本体）：本轮运行上下文注入的 AGENTS.md §1 即
"## 1. 接任务前 7 问(必答,不答不写)"，其下是"不改变契约/改变契约/改变闭集"
的动作表与"不变量与契约正确 → … → '少改几行'的幻觉"优先级。换句话说，
0255 §0 不是建议书，是生产实例每轮上下文顶部的受理门——连本轮 iter-arch 的
铁律（"开工拿锁先 git status，脏树只读不动"）都是这一机制的实例化。

## 1. LCA 现状（实证，2026-10-02）

### 1.1 7 问条文存在，但只面向"写代码的人"

根 `AGENTS.md` §1（line 23 起）有同样的 7 问条文，落地点是
`docs/agent-contract/coding-guardrails.md`（"写代码任务的 standing rule"）。
这是**工程纪律**，约束的是人类工程师 / 编码 agent 写代码前的自检。

### 1.2 run 时 agent 的 prompt 装配里：零命中（实证缺口）

- `grep "7问|接任务前" lca/plugins/prompts/ lca/nodes/` → **零命中**；
- `grep "受理|必答|intake" lca/plugins/prompts/sections/` → **零命中**；
- `lca/nodes/plan/compose.py` 是 TaskList 台账节点（ADR-0228 §Decision 3，
  首 turn seed task list / 其后 bump revision），**不是受理问答**；
- react_prompt 19 段（`template_provider.py`）无任何"任务受理"义务段；
  对比：`memory_retrieval` 段甚至是可选的（fallback ""，0265 D3 已记录为盲区）。

### 1.3 结论

LCA 的任务受理 = "直接进 react 循环"，首 turn 没有任何强制的前置判断。
后果形态（可观察的风险，非已发生事故）：

1. **边界声明缺失**：任务触及哪层/哪进程/哪信任边界，首 turn 无显式答案，
   跨边界操作靠模型临场自觉（与 0256 审批面的"触发条件靠机制"思想相悖）；
2. **幂等语义后置**：7 问第 6 问（失败/重试/幂等）本应先行声明，LCA 的 run
   轨迹里这类声明只在出错后复盘时出现；
3. **受理与否不可审计**：0258 的压缩豁免要求 standing 永不进压缩流，
   但"任务被接受时的前置判断"本身没有轨迹落点——回放时无法回答"当初为什么
   认为可以这么干"。

## 2. 契约（草稿）

### C1 首 turn 必答义务块（硬契约）

react_prompt 首 turn 强制渲染"受理 7 问"义务段：**不可选、不可 fallback 为空**。
"必答，不答不写"字面语义 = 首个 tool_call 发出前，轨迹里必须有 7 问答案。
这是 0255 §0 的直接移植；与 0265 D3 的 `memory_retrieval` 可选语义形成对照
（义务段不得可选，0265 C3 语义分级的实例化）。

### C2 7 问的 run 时形态（不照搬写代码版）

面向 agent 任务受理的精简版（不是根 AGENTS.md §1 的工程措辞）：

1. 问题是什么（任务边界 / 显式非目标）；
2. 触及的事实/契约/SSOT 在哪（唯一真值指针）；
3. 改变哪个边界（层 / 进程 / 外部系统 / 信任边界）；
4. 失败·重试·幂等语义先行声明；
5. 不可逆动作清单（对应 0256 审批面的前置输入）；
6. 验证方式（如何证明做对了）；
7. 已有机制能否表达（不造平行机制，AGENTS.md §1.5 的"现有 Protocol 能否表达"下沉）。

### C3 fail-closed 分支

答案触及"改变闭集 / 层边界 / SSOT / 能力模型" → **停止执行，先出方案**
（把工程 AGENTS.md §1 动作表"停止编码，先提交 ADR/Note 草案"下沉为 run 时行为）。
不改变契约 → 直接执行。分支判定本身落轨迹（C4）。

### C4 答案落轨迹

7 问答案写 journal evidence（与 0258 C2 血统衔接：受理判断的血统是首 turn 的
任务原文 + 7 问答案）。后续 turn 的压缩/回放可审计受理时的前置判断。

## 3. 验收

- **T1**：首 turn system 必含受理义务块且非空（模板 + 渲染断言；对照 T1 的红队：
  删义务块 → 测试红）。
- **T2**：改契约类任务的轨迹含 stop + 方案输出、且无 tool_call（C3 fail-closed
  分支真生效；轨迹断言）。
- **T3（红队，可选）**：诱导模型跳过 7 问直接写副作用 → 断言被 C1/C3 拦下，
  或至少轨迹留痕（C4）。

## 待拍板（只提案，不擅自决定）

1. **落点形态**：纯提示级义务（0255 形态，原样照抄，靠模型自觉）vs
   节点级强制拦截（首 tool_call 前置检查，未见受理答案则拒发——硬 gate，
   muse 思想"能用代码强制的不用 prompt 提示"）。
2. **7 问内容**：精简 run 时版（C2）还是直接引用根 AGENTS.md §1 原文
   （写代码版措辞对 run 时任务偏工程，读起来别扭）。
3. **适用范围**：所有任务（含只读问答）vs 仅带写副作用/跨边界任务
   （只读问答强制 7 问可能是噪音；但"只读"本身也需要第 5 问的不可逆清单吗——待议）。
