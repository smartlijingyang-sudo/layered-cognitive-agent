# ADR-0272：实时信息路由铁律契约

## 状态

**Proposed — 2026-10-02**

> **一句话**：search 摘要永远只是线索，不是证据——"当前状态/价格/库存/账号内数据"必须走真机或 skill 实查；无实查轨迹就不许下"当前"断言。ADR-0255 §3.3（browser.* 路由铁律）+ §6 T7 的 LCA 落地提案。

## 0. 背景：生产 Muse 的 §3.3 与 T7

0255 §3.3 定义三类通道与路由铁律：

- `browser.search` / `browser.open` / `browser.find`——信息查询通道（search 结果**不许**当作"有货/可订"的证据）；
- `browser.spawn_task` / `steer_task`——**真机**通道（登录/表单/下单/实时核验；任务书自包含：目标/约束/成功标准）；
- skill——已授权能力的实查通道。
- **路由铁律**：信息查询走 search/open；凡是"当前状态/价格/库存/账号内数据"走真机或 skill；search 结果**不许**当作"有货/可订"的证据。

0255 §6 **T7 工具路由**（验收锚点）：给一个"查某商品现在有没有货"的问题 → 走真机/skill 实查，不许用 web 搜索摘要断言"有货"。

### 1.2 路由纪律：零机制（实证缺口）

- 全系 ADR（0256–0268）grep"路由铁律/实时核验通道/spawn_task 任务书"**零命中**——§3.3 从未被 ADR 评估。
- prompt 段无"实时核验必须走实时通道"纪律（`lca/plugins/prompts/sections/` grep"有货/可订/实时核验"零命中）。
- `web_search` 工具无证据弱化声明：返回的搜索摘要与真机实查结果在下游无区分标记。
- `BrowserSubagent.execute_action(session_id, action)` 执行**单步** `BrowserAction`，无任务书三要素校验——"查一下有没有货"这类模糊委托可直达真机通道（0257 只覆盖 subagent 委派信封，未覆盖 browser 真机通道委托）。

## 2. 实证缺口

- **G1（路由二分无契约）**："查某商品现在有没有货"走哪个通道，靠模型自觉，无机制强制。
- **G2（search 证据纪律无契约）**：0262 C2 是 skill 检索的否定证据纪律（检索失败≠检索无结果）；但 search 通道的两条无人管——(a) 搜到摘要≠当前有货（肯定证据弱化）；(b) 搜不到≠没有（否定证据纪律在 search 通道的缺席）。
- **G3（真机任务书无校验）**：browser 通道委托无"目标/约束/成功标准"三要素门，模糊委托直达真机。

## 3. 契约（草稿）

### C1 查询 vs 核验路由二分（硬契约）

问题语义含"当前状态/价格/库存/账号内数据"（"现在有没有货""当前价格""我的订单到哪了"）→ **必须**走真机（browser 工具/BrowserSubagent）或 skill 实查；用 `web_search` 摘要直接回答 = 违规。

muse 思想：能用代码强制的不用 prompt 提示——C1 是轨迹可验证的（见 T1），走硬契约。

### C2 search 结果证据纪律

- **C2a（硬契约，fail-closed）**：无真机/skill 实查轨迹时，不许输出"当前有货/无货/可订/当前价格"类**当前态断言**；要么实查，要么明确标注"未实查，仅为搜索线索"。违反 = 测试红（轨迹断言，见 T2）。
- **C2b（提示级义务）**：搜到摘要只能表述为"搜索摘要显示……"，不许省略证据弱化语后当作事实陈述。这是模型表述行为，轨迹难判定，走提示级（prompt 段义务块）。
- 与 0262 C2 的关系：0262 C2 管 skill 检索的否定证据；C2 管 search 通道的肯定弱化 + 否定纪律。两条是兄弟条目，不重复。

### C3 真机任务书自包含（硬契约）

browser 真机通道的委托必须带三要素：**目标**（要核验什么当前态）/ **约束**（不许下单/不许改账号等）/ **成功标准**（什么算"查到了"）。缺要素 → 通道入口 `validate` 拒绝，不进真机。这是 0257 委派信封思想在 browser 通道的应用（0257 管 subagent 委派，C3 管真机委托）。

### C4 账号内数据走 skill 优先

- **什么数据**：用户账号内数据——订单/余额/订阅/预约记录等 connector 背后的数据（非公开网页可查）。
- **和什么冲突**：与"search 凑合答"的懒惰路径冲突；与"真机登录账号"的重通道冲突（真机登录要过 CAPTCHA/二次验证，成本高）。
- **代价**：skill 实查每次调 connector（慢 + 配额消耗）；search 快但证据弱，只能做线索。
- **优先级**：已授权 skill > 真机 > search 摘要。skill 不可用时的降级顺序（真机登录 vs 明确说查不到）待拍板（提案③）。

## 4. 验收

- **T1**（0255 §6 T7 轨迹验收）："查某商品现在有没有货"类问题 → run 轨迹必须含 browser 工具调用或 skill 实查调用；最终回答中的"有货/可订/当前价格"断言必须有实查轨迹证据（断言→轨迹证据指针，呼应 0257 的 evidence 指针思想）。
- **T2**：无实查轨迹却输出"当前无货/有货"断言 → 违规（C2a fail-closed）。
- **T3**：browser 委托缺目标/约束/成功标准任一要素 → 通道入口拒绝（C3）。

## 待拍板（只提案，不擅自决定）

1. **独立 ADR vs 并入 0262**：arch 轮建议**独立**。核心条目 4 条（C1/C2/C3/C4），与 0262 的耦合点只有"skill 是实查通道之一"；0262 主题是 skill 发现与沉淀协议，0272 主题是实时信息通道选择纪律——并入会稀释 0262 的发现主题。但若评审认为体量不足，可降级为 0262 的 §X 修订。
2. **硬契约 vs 提示级**：建议 C1/C2a/C3 走硬契约（轨迹/入口可验证），C2b 走提示级（表述措辞是模型行为，难做轨迹断言）。
3. **账号内数据的降级顺序**：skill 不可用时，走真机登录（重通道，需用户授权）还是直接说"查不到"？涉及凭证与用户打扰成本，需产品拍板。
