# ADR-0259 — 时间戳信任与日期推导契约：now 的唯一来源、日期推导工具验证、事件时间与记录时间分离

## 状态

**Proposed — 2026-10-01**

> **一句话**：Muse 侧"now=本 turn 时间戳、星期/日期推导一律 date -d 验证、事件时间 vs 记录时间 vs 检索时间三者区分"三条规则，LCA 侧第一条已落地为代码（§1.4 developer 时间戳 + CURRENT_DATE 注入），后两条是空白——本 ADR 把"now 的唯一来源"升为契约，并为日期推导补上"必须经可信工具验证、不得凭模型时间感推算"的硬性规则，以及"陈述事件时间必须引事件字段"的 provenance 纪律。

**Extends**：
- [ADR-0255](0255-muse-production-runtime-full-reference.md)（Muse 生产运行时全量参考）：本 ADR 是 0255 §4.7（时间戳信任）的 LCA 落地提案——对应 0255 §1.4 的 developer 时间戳锚点则已有实现（见下）；
- [ADR-0254](0254-commercial-context-files-and-continuous-memory-runtime.md)：时间戳锚点位于 §1.4 的注入块，与 0254 的 standing 文件体系同属每 turn 注入；
- [ADR-0037](0037-journal-as-truth.md)：C3 的"事件时间 ≠ 记录时间"依赖 journal 的事件-原文真值链（记录时间 ≠ 事件时间）。

**实证来源**：2026-10-01 iter-arch 轮对当前实现的实证审计——

- 已落地（升 C1 的基础）：
  - `lca/plugins/prompts/sections/runtime_env.py::render_developer_timestamp`：渲染 `[Thu 2026-10-01 23:09:06 CST] [client_timezone=...]` 锚定"now"（0255 §1.4）；
  - `lca/plugins/prompts/sections/time.py::CurrentDateSection`：`clock_from_manifest` 取时钟 payload，无时钟时显式标注 `(未知当前时间)`（"无锚点不装懂"，与 §4.7"不许用模型时间感"同源）；
- 缺口一（date -d 验证空白）：全仓库 `date -d` 零引用；prompt 里没有任何"日期推导必须经工具验证"的规则；shell 工具是今天唯一能跑 `date` 的通道，但 shell 域挂 `REQUIRE_APPROVAL`（ADR-0256 Task 5，a1c20526d）——模型要验证"三天后是星期几"要么走审批（摩擦）、要么凭时间感直接答（风险）。**没有免审批的只读时钟验证路径**；
- 缺口二（事件时间无纪律）：检索/引用链中没有"事件发生时间 vs 记录/检索时间"的区分规则；journal 事件的 `occurred_at`（若有）与索引/投影时间的关系未写进任何提示或契约，模型说"X 发生在 9 月 30 日"时，依据的是哪种时间不可审计。

## 0. 接任务前 7 问

1. **问题是什么？** ① "now 已锚定"只靠注入实现，模型仍可凭训练时间感推算星期/日期偏移，无人拦截；② 日期验证的唯一工具通道是走审批的 shell，验证成本高于犯错成本；③ 陈述事件时间时依据哪种时间无规则可循。
2. **受影响的事实或契约是什么？** developer 时间戳的"now 锚点"语义、shell 域审批策略（0256）、工具目录的只读工具分类、检索回答的时间引用规范。
3. **唯一真值在哪里？** 当前时间的真值是本 turn 的 developer 时间戳（注入值），不是模型训练数据；事件发生时间的真值是描述该事件的字段（原文/journal），不是索引时间、检索时间或消息时间。
4. **改变哪个边界？** 把"日期推导"从"模型自由发挥"变成"必须经可信工具验证的推导"；把"事件时间"从"随手写个日期"变成"必须标注来源字段"。
5. **现有 Protocol / ADR 能否表达？** 不能。`time.py` 的 `(未知当前时间)` 只管"有无锚点"，不管"锚点之后怎么推导"；`memory.py` 的检索义务只管"查什么"，不管"时间怎么说"。
6. **失败、重试、恢复和幂等语义是什么？** 验证工具调用失败 → 不得退回模型时间感作答，fail-closed：明确标注"日期未经验证"或跳过该日期断言；事件时间字段缺失 → 不得用记录时间冒充，陈述时必须标注时间来源（或缺失）。
7. **如何验证？** §4 的验收用例 T1–T3。

## 1. 契约

### C1 — "now" 的唯一可信来源是本 turn 的 developer 时间戳（已实现，升不变量）

- 任何需要"现在是何时"的判断，唯一合法依据是注入的 developer 时间戳（`[weekday YYYY-MM-DD HH:MM:SS tz]` 行）与 `CURRENT_DATE` 块；
- `time.py` 的"无时钟 → 显式标注未知"语义保留：**没有锚点时不许装有时间感**；
- 模型的时间感（训练数据里的"今天"）与锚点冲突时，以锚点为准；提示词必须有一条模型可见的硬性声明（见 §2 落地方式）。

### C2 — 日期推导必须经可信工具验证

- 凡回复中包含**星期几判定、日期加减、相对日期换算**（"三天后""下周一""昨天"→具体日期）的，必须先调用可信时钟/日期工具验证，再输出结论；
- **不许**凭模型时间感直接推算星期几；不许从训练数据推算"今天星期几"；
- 验证失败（工具不可用/报错）时 fail-closed：要么明确标注"（日期未经验证）"，要么不输出该日期断言——**不许退回时间感**；
- 验证工具必须是只读、确定性、无副作用的（见 §5 待拍板形态）。

### C3 — 事件时间 vs 记录时间 vs 检索时间三者分离

- 陈述"X 发生在 T"时，T 必须来自**描述该事件的字段**（原文/事件 `occurred_at`-类字段），并可追溯；
- 不许用 journal 索引时间、消息到达时间、检索执行时间冒充事件发生时间；
- 事件字段缺失时：陈述必须标注时间来源（如"记录时间为 …，事件发生时间未记录"），不许静默替换。

## 2. 落地方式（提案级，细节待拍板后实施）

1. prompt 新增模型可见硬块（建议挂在 `time.py` 的 `CurrentDateSection` 渲染后，或独立 `time_discipline` section）：
   - "本 turn 的 now 以 developer 时间戳为准；凡需星期/日期推导，先调用日期验证工具，验证失败则标注未验证"；
2. 日期验证工具的形态（§5 待拍板）；
3. 检索回答模板（`memory.py` 的检索义务块）追加 C3 一行：时间断言必须标注来源字段。

---

## 3. 非目标

- 不改 developer 时间戳的注入格式（C1 只升契约，不改代码）；
- 不碰 shell 域的 REQUIRE_APPROVAL（验证工具若走独立通道，审批策略不变）；
- 不要求历史数据补 `occurred_at`（C3 只约束**新陈述**的纪律，老数据按"来源缺失"标注处理）。

---

## 4. 验收用例

- **T1**：prompt 装配产物中含时间纪律硬块（模型可见）；无时钟 manifest 时仍渲染 `(未知当前时间)` 且不出现日期推导断言；
- **T2**：构造"今天是周四，三天后是周几"类用例——run 轨迹中必须出现日期验证工具调用；工具被禁用时，回复含"未经验证"标注而非直接给出星期；
- **T3**：检索回答中含事件时间断言时，断言附带来源字段引用；来源字段缺失时含"记录时间≠事件时间"的显式标注。

## 5. 待拍板（arch 轮不擅自决定）

1. **验证工具形态**：新增 core 域只读工具（如 `clock_now` / `date_offset`，免审批、确定性）vs 在 shell 域给 `date` 命令开免审批白名单（审批策略开口子）vs 纯提示词约束不给工具（弱约束，倾向否决）。倾向第一种；
2. **C2 的硬块落点**：并入 `CurrentDateSection` 渲染 vs 独立 `time_discipline` section（后者可单独开关）；

## 7. 决策记录（2026-10-02，李超授权 Athena 按 muse 思想裁决）

1. **验证工具形态：core 域只读工具（`clock_now`/`date_offset`），免审批**。理由：机制 > 自觉（纯提示词是自觉，否决）；shell 白名单是给审批策略开口子（fail-open 方向）；core 只读工具无副作用，符合 0256“读不审”哲学。
2. **C2 硬块落点：独立 `time_discipline` section**（不并入 CurrentDateSection）。理由：“now 锚定”与“推导纪律”是两种职责，混排违反关注点分离；独立 section 可单独开关。
3. **CURRENT_DATE 锚定 turn 版本：暂不**，YAGNI（与 ADR 倾向一致）。
